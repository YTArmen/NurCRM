## 1. Старт приложения одним запросом

**Сейчас** после входа клиент делает подряд:

1. `auth/login`;
2. `users/profile`;
3. `users/company`;
4. `users/settings/company` (весы);
5. `construction/cashboxes`;
6. `construction/shifts/?status=open`;
7. каталог.

Плюс права (часть 19) и функции (часть 19). На телефоне без 4G это 3–4 с белого экрана.

**Нужно:**

```
GET api/main/bootstrap/?cashbox_id=<id>&device_id=<id>
→ {
  "server_time": "2026-10-13T07:35:41Z",
  "user": {id, full_name, role, role_display, is_owner, branch_id},
  "company": {id, name, market_sphere, currency, tariff, logo_url, receipt_header, receipt_footer},
  "permissions": [...],                  // часть 19
  "features": {...},                     // часть 19
  "cashboxes": [{id, name, branch_id}],
  "shift": {...} | null,                 // открытая смена этого кассира на этой кассе, с итогами (раздел 6)
  "catalog_version": 18342,              // раздел 2
  "settings": {scale_barcode_layout, scale_barcode_mode, rounding, min_stock_default, ...}
}
```

- Ответ ≤ 300 мс (p95).
- `login` может сразу возвращать то же поле `bootstrap`, если передан `?bootstrap=1`. Тогда вход — один запрос.
- `server_time` нужен для разделов 8 и 11 (время продажи без связи и подпись обмена по сети: часы не должны расходиться больше 10 минут).

## 2. Каталог: скорость и объём

### 2.1. Только изменения

Часть 27 (раздел 8) просит `updated_after`. Этого мало: без удалённых товаров клиент продолжает продавать удалённое. Нужно:

```
GET api/main/products/list/?updated_after=<catalog_version>&page_size=1000
→ { "catalog_version": 18342, "count": 37, "next": null,
    "results": [...изменённые и новые...],
    "deleted": ["uuid", "uuid"] }
```

- Ключ — **`catalog_version`** (целое, растёт с каждым изменением товара, цены, остатка, штрихкода, фото), а не время: часы клиента и сервера расходятся.
- Изменение остатка продажей тоже поднимает версию. Иначе полная синхронизация нужна после каждой продажи на соседней кассе.
- Без `updated_after` — полный список, как сейчас.

### 2.2. Только остатки

Остаток меняется в сотни раз чаще, чем карточка товара. Нужен лёгкий запрос:

```
GET api/main/products/stock/?updated_after=<stock_version>
→ { "stock_version": 9911, "items": [{"id": "...", "q": "12.000", "v": [{"id": "<variant>", "q": "3"}]}] }
```

Один товар — около 60 байт вместо 1–2 КБ полной карточки. Касса и телефон опрашивают его каждые 30–60 с, а полный каталог — раз в 5 минут или по событию `catalog.changed` (часть 27, раздел 1).

### 2.3. Лёгкие поля

`GET products/list/?fields=lite` → только:

- `id`, `name`, `price`, `wholesale_price`, `unit`, `is_weight`, `is_service`;
- `barcode`, `alternate_barcodes`, `sku`, `plu`;
- `quantity`, `category`, `is_favorite`;
- `thumb_url`;
- `packages` (поштучно);
- `variants` (кратко — раздел 2.5).

Описание, история цен, поставщики, характеристики — только в карточке товара `GET products/{id}/`.

### 2.4. Сжатие и кэш

| Мера | Ожидаемый эффект |
|---|---|
| `Content-Encoding: gzip` или `br` для JSON больше 1 КБ | Каталог 10 000 товаров: ~12 МБ → ~1,5 МБ |
| `ETag` / `If-None-Match` → `304 Not Modified` на `products/list/`, `bootstrap/`, `categories/` | Повторная проверка без тела ответа |
| `Cache-Control: public, max-age=31536000, immutable` на фото и миниатюрах (имя файла с хэшем) | Фото качаются один раз |
| HTTP/2 и keep-alive на балансировщике | Параллельные запросы телефона без новых соединений |
| `page_size` до 1000 для каталога (сейчас клиенты берут по 300) | В 3 раза меньше запросов |

### 2.5. Миниатюры и варианты в списке

- **`thumb_url`** — 256 × 256, WebP, ≤ 15 КБ, создаётся при загрузке фото. Сейчас касса и телефон качают оригинал (бывает 2–4 МБ) ради плитки 64 × 64. На складе на 300 товаров это сотни мегабайт.
- **`variants`** в списке товаров: `[{id, size, color, barcode, price?, quantity, is_active}]`. Сейчас касса спрашивает варианты по одному товару (`products/{id}/variants/`) с ожиданием до 4 с на каждый и держит свой индекс штрихкодов вариантов (`variant_barcodes.json`, фоновая проверка 1,5 с на товар). Части 25 (А) и 27 (раздел 8) описывают сами варианты; здесь — отдавать их **в списке** и искать по ним штрихкод.

### 2.6. Поиск по штрихкоду

`GET api/main/products/barcode/{code}/` должен находить:

- основной штрихкод;
- дополнительные (`alternate_barcodes`);
- штрихкод варианта (часть 27);
- весовой штрихкод по настройке компании: вернуть товар и вес.

Ответ ≤ 100 мс (индекс по всем штрихкодам).

## 3. Остаток — изменение на величину и с ключом (P0, потеря данных)

**Сейчас** приёмка без поставщика (касса — `PurchaseReceivingService`, телефон — «Приёмка сканером») делает так:

1. `GET products/{id}/` — прочитать остаток.
2. `PATCH products/{id}/ {quantity: остаток + принято}`.

Если между шагами 1 и 2 соседняя касса продала или приняла этот товар, её изменение **затирается**. Повтор после обрыва связи **прибавляет дважды**. Телефон частично защищается: отмечает строки по одной. Но гонку двух устройств клиент исправить не может.

**Нужно** — изменение остатка документом, на величину, с ключом:

```
POST api/main/stock/movements/
Idempotency-Key: <uuid>
{ "kind": "receive" | "write_off" | "count_fix" | "return_to_supplier",
  "reason": "текст", "branch_id": "...", "source": "kassa" | "phone" | "web",
  "lines": [{"product_id": "...", "variant_id": null, "delta": "24.000", "purchase_price": null}] }
→ { "id": "...", "number": "ПР-000123",
    "lines": [{"product_id": "...", "before": "12.000", "after": "36.000"}],
    "catalog_version": 18343 }
```

- Изменение атомарно: `UPDATE … SET quantity = quantity + delta` в одной транзакции на все строки.
- Повтор с тем же ключом возвращает тот же ответ (часть 27, раздел 4).
- Документ виден в журнале склада сайта — кто, когда, с какого устройства.
- `PATCH products/{id}/ {quantity}` оставить для «точного количества» администратором, но писать документом `count_fix`.

**Ревизия** (`inventory/sessions/`) тоже должна принимать `Idempotency-Key`. Сейчас повтор после обрыва создаёт вторую сессию, и администратор видит две одинаковые ревизии.

## 4. Машинные коды ошибок (P0)

**Сейчас** ответы 400/409/502 — русский текст, и клиенты ищут в нём слова. Например, касса ловит `502` с текстом «Возвращено позиций» при возврате. Любая правка текста на сервере ломает кассу.

**Нужно** — единый формат всех ошибок:

```json
{ "code": "insufficient_stock",
  "detail": "Товара «Mars» осталось 2 шт.",
  "fields": {"items[0].qty": ["Больше остатка"]},
  "data": {"product_id": "...", "available": "2"} }
```

Обязательный список кодов (дополнять по мере надобности, коды не переименовывать):

| Код | Когда |
|---|---|
| `shift_not_open`, `shift_closed`, `shift_of_other_cashier` | Продажа, возврат, внесение без своей открытой смены |
| `insufficient_stock` | Нет остатка (`data.available`) |
| `price_changed` | Цена в запросе отличается от цены сервера (`data.server_price`); раздел 8.3 |
| `total_mismatch` | Итог сервера ≠ итог клиента (`data.server_total`) |
| `no_debt`, `debt_overpay` | Оплата долга: долга нет / сумма больше долга |
| `already_returned`, `return_qty_exceeds` | Возврат |
| `idempotency_conflict` | Тот же ключ с **другим** телом (раздел 8.4) |
| `device_revoked`, `token_expired` | Сессия (часть 27, раздел 2) |
| `tariff_limit`, `feature_disabled` | Функция выключена или вне тарифа (часть 19) |
| `rate_limited` | 429 вместе с `Retry-After` (часть 27, раздел 9) |
| `validation_error` | Ошибки полей (`fields`) |

`detail` — на языке из заголовка `Accept-Language` (ru, ky, en, tr, uz), иначе по-русски.

## 5. Чеки: фильтры и состав одним ответом

### 5.1. Фильтры списка

```
GET api/main/pos/sales/?shift=<id>&cashbox=<id>&cashier=<id>&created_after=&created_before=
                       &status=paid,partially_returned&number=1115&client=<id>&page_size=100
```

- **Сейчас** телефон («Мои чеки» за смену) и касса («История чеков» — смена, сегодня, вчера) грузят общий список компании и фильтруют у себя. В магазине с тремя кассами это 3–5 страниц ради 20 чеков.
- `number` — постоянный номер чека (часть 20, раздел 2).
- Сортировка стабильная: `-created_at, -id`. Курсор `?cursor=` вместо номера страницы (часть 27, раздел 9: страницы «съезжают», когда во время листания проходит новая продажа).

### 5.2. Строка списка

Сейчас в строке нет состава, и для поиска чека по товару касса открывает каждый чек.

Добавить в строку:

- `items_count`;
- `items_preview` — до 3 названий;
- `payments` — разбивка по способам (часть 20, раздел 3);
- `refunded_amount`;
- `cashier_name`;
- `cashbox_name`.

### 5.3. Состав и печатная форма

```
GET api/main/pos/sales/{id}/?expand=items,payments,returns,client
```

Ответ — одним запросом. Сейчас для возврата касса дополнительно зовёт:

- `pos/returns/?sale=` — чтобы узнать, сколько вернул сервер;
- «движение денег возврата» — чтобы узнать, сколько выдать.

`GET pos/sales/{id}/receipt/` — сейчас только текст. Нужен ещё **структурный** вид (`?format=json`):

- реквизиты компании;
- строки: название, кол-во, цена, скидка, сумма;
- итоги и оплаты;
- номер, кассир, ККМ (часть 20).

Телефон собирает из него чек для WhatsApp и Bluetooth-принтера, касса — для повторной печати. Не нужно три разных построителя чека в клиентах.

## 6. Текущая смена одним запросом

```
GET api/construction/shifts/current/?cashbox=<id>
→ { id, status, opened_at, cashier, cashbox, opening_cash, expected_cash,
    sales_total, sales_count, by_method: {cash, card, qr, debt, mixed_cash, mixed_card},
    returns_count, returns_sum, cash_in, cash_out, debt_payments }   // поля — часть 27, раздел 7
→ 404 {"code": "shift_not_open"} — смены нет
```

**Сейчас:**

- клиенты берут `shifts/?status=open` (иногда несколько страниц) и ищут свою смену по кассе;
- касса держит кэш списка открытых смен на 30 с, чтобы не делать это после каждой продажи.

Ответ ≤ 150 мс. Этот же объект — в поле `shift` из `bootstrap` (раздел 1) и в ответе `pos/checkout/` (`"shift": {...}` после продажи). Тогда шапка «в кассе N сом» обновляется без второго запроса.

## 7. Долги клиента одним запросом

**Сейчас** окно «Оплата долга» (касса, новый десктоп) делает:

- `pos/sales/?status=debt&client=` — список;
- для каждой продажи — `pos/sales/{id}/` (ради `deal_id`) и `clients/{id}/deals/{deal}/` (ради `remaining_debt` и взносов).

Это 1 + 2 × N запросов. У клиента с 10 долгами — 21 запрос и 3–5 с ожидания.

**Нужно:**

```
GET api/main/clients/{id}/debts/
→ { "total": "110444.60",
    "items": [{"sale_id", "number", "created_at", "first_item_name",
               "original": "110127.00", "paid": "0.00", "remaining": "110127.00",
               "deal_id", "installments_left": 3, "next_due": "2026-10-20"}],
    "history": [ ...полностью оплаченные за 90 дней... ] }
```

Оплата — уже есть: `clients/{id}/pay-debt/` и `pos/sales/{id}/pay-debt/` с `Idempotency-Key`. Ответ оплаты должен сразу возвращать новый `items` (как выше), чтобы клиент не перечитывал список.

## 8. Продажа одним запросом — доработки `pos/checkout/`

**Поправка к части 27, раздел 5.** Продажа одним запросом уже работает на сервере: `POST api/main/pos/checkout/` с `Idempotency-Key` (BE-11, проверено 28.09). Касса и телефон ведут через него все продажи. Новый адрес `checkout-full` **не нужен**. Нужны доработки существующего.

### 8.1. Время продажи без связи

Чек из очереди без интернета досылается через минуты или часы. Сервер ставит время досылки, поэтому чек попадает не в тот час, иногда в другой день или другую смену после 01:00.

- Принимать `sold_at` (ISO 8601, UTC).
- Если `sold_at` старше 72 часов или в будущем больше чем на 10 минут — `400 validation_error`.
- Смена — та, что указана в `shift`, даже если она уже закрыта автоматически в 01:00. Сейчас такой чек отклоняется, и кассир видит «Некорректные чеки».

### 8.2. Что сейчас идёт только старым путём (3–5 запросов)

| Случай | Нужно в `pos/checkout/` |
|---|---|
| Поштучно из пачки | `items[].package_id` (как в `add-item`) |
| «Расход» — доп. услуга с отрицательной ценой | `items[].custom` с `price < 0` и `kind: "expense"` или отдельный запрос внесения/изъятия; сейчас «Укажите цену позиции» |
| Комплект (локальный, не UUID) | `items[].bundle_id` или раскладка комплекта на сервере |
| Скидка суммой на чек, которую сервер отклоняет пятисоткой | Принимать `order_discount_total` без 500 (касса сейчас раскладывает её по строкам) |

### 8.3. Проверка без проведения

`POST api/main/pos/checkout/?dry_run=1` — тот же расчёт без записи:

- `{server_total, lines[] с ценой и акцией сервера, warnings: [price_changed, insufficient_stock]}`;
- ≤ 150 мс.

**Зачем.** Денежный баг продажи №1136 (28.09): кассир взял 50,00, а сервер провёл 42,50 — применил акцию, о которой касса не знала. Сейчас касса сверяет итог сама и при расхождении уходит старым путём. С `dry_run` окно оплаты сразу показывает сумму сервера.

### 8.4. Ключ с другим телом

Сейчас повтор с тем же `Idempotency-Key` и **другим** составом возвращает прежнюю продажу (проверено 28.09). Это опасно: клиент думает, что провёл новый чек.

Нужно:
- хранить хэш тела запроса вместе с ключом;
- другой хэш → `409 {"code": "idempotency_conflict"}`.

### 8.5. Ответ продажи

В ответ `pos/checkout/` добавить:

- `number` (часть 20);
- `shift` — итоги смены (раздел 6);
- `stock` — `[{product_id, variant_id, quantity}]`, новые остатки проданных товаров;
- `catalog_version`.

Тогда касса и телефон обновляют шапку и остатки без отдельных запросов.

### 8.6. Пачка из очереди

`pos/checkout/batch/` (уже есть, до 50 продаж) — подтвердить в документации порядок проведения: по `sold_at`, затем по порядку в запросе. Ответ — по каждой продаже отдельно.

## 9. Отложенные чеки на сервере

**Сейчас** отложенные чеки хранятся в файле на кассе (`deferred_carts.json`). Телефон их не видит, а при переустановке кассы они пропадают.

```
ParkedCart — id, company_id, branch_id, cashbox_id?, created_by, label, client_id?,
             lines (json, как тело pos/checkout), order_discount, created_at, updated_at, expires_at (по умолчанию 3 дня)
GET    api/main/pos/parked-carts/?branch=
POST   api/main/pos/parked-carts/            (Idempotency-Key)
PATCH  api/main/pos/parked-carts/{id}/
POST   api/main/pos/parked-carts/{id}/take/  → тело для checkout; чек больше не виден другим (блокировка 30 мин)
DELETE api/main/pos/parked-carts/{id}/
```

- Резерв товара отложенного чека — часть 27, раздел 6 (`source: deferred_cart`).
- Событие `parked_cart.changed` (часть 27, раздел 1).

## 10. Скорость сервера

### 10.1. Цели по времени ответа (p95, при 10 000 товаров и 50 000 продаж в компании)

| Запрос | Сейчас (замеры кассы) | Цель |
|---|---|---|
| `auth/login` | ~400 мс | ≤ 300 мс |
| `bootstrap` (раздел 1) | — (5–7 запросов, 1,5–3 с) | ≤ 300 мс |
| `pos/checkout/` | 0,8–1,9 с (журнал кассы 28.09, 04.10) | ≤ 400 мс |

### 10.3. Без N+1

Проверить сериализаторы списков (продажи, товары, клиенты, смены) на запрос к базе в каждой строке: `select_related` и `prefetch_related` для кассира, кассы, клиента, категории, бренда, фото.

Критерий: число запросов к базе на страницу списка не зависит от размера страницы. Проверка — тестом с подсчётом запросов.

### 10.4. Тяжёлое — заранее

- Итоги смены (раздел 6) — считать при каждой продаже и движении денег, а не суммировать продажи при каждом запросе.
- Аналитика за прошлые дни — дневные агрегаты (по товару, категории, кассиру, способу оплаты), пересчёт ночью и при возврате задним числом.
- «Сегодня» — по живым данным.

### 10.5. Ограничения частоты

Часть 27 (раздел 9) просит `Retry-After` и опубликованные лимиты. Дополнительно:

- **Лимит по устройству, а не только по токену.** Сейчас касса и программа владельца на одном компьютере делят один лимит и мешают друг другу. С отдельными лимитами касса досылает очередь без интернета пачкой, а владелец в это время смотрит сводку.
- **Продажи (`pos/checkout/`, `checkout/batch/`) — отдельный, более широкий лимит.** Продажу нельзя задерживать из-за того, что программа владельца выгружает аналитику.

## 11. Служебное

### 11.1. Здоровье сервера

`GET api/health/` → `{"ok": true, "db": "ok", "time": "…", "version": "…"}`. Без токена, ≤ 50 мс, не входит в лимиты.

Сейчас касса узнаёт об аварии по таймаутам продаж (`ServerOutageMonitor`, окно 5 с). Это значит, что кассир ждёт, а только потом касса переходит в работу без интернета.

### 11.2. Время сервера

Заголовок `Date` (или `X-Server-Time`) в каждом ответе. По нему клиент:
- поправляет `sold_at` (раздел 8.1);
- предупреждает о часах, которые отстают больше чем на 10 минут: обмен по локальной сети отвергает такие подписи.

### 11.3. Номер запроса

Клиент присылает `X-Request-Id: <uuid>`, сервер возвращает его в ответе и пишет в свой журнал. Тогда по жалобе «чек не прошёл в 14:32» журнал кассы и журнал сервера сводятся за минуту.

### 11.4. Журнал медленных запросов и тревоги

| Что | Как |
|---|---|
| Журнал медленных запросов | Всё дольше 1 с, с телом без персональных данных и токенов |
| Ежедневная сводка p50/p95/p99 по адресам раздела 10.1 | Для команды бэкенда |
| Тревога | 5xx больше 1 % за 5 минут или p95 `pos/checkout/` больше 1 с |

## 12. Клиенты

### 14.1. QR на экране кассира → покупатель сразу скачивает чек PDF (запрос владельца 13.10)

Владелец: «QR при скане — скачивался чек в виде PDF». Телефон уже показывает QR и сам собирает PDF для отправки в мессенджер, но чтобы камера покупателя **скачала файл**, нужна публичная ссылка на PDF. Без неё QR несёт только текст чека.

Часть 20, раздел 8, уже описывает `GET public/e-receipt/{token}.pdf`. Не хватает четырёх вещей:

1. **Ссылка у каждой продажи, а не только при `send_e_receipt`.** Ответ `pos/checkout/`, `pos/sales/{id}/` и строки списка продаж отдают `e_receipt: {token, url, pdf_url}`. Телефон читает `e_receipt.pdf_url` (и запасные `e_receipt_pdf_url`, `e_receipt_url`, `e_receipt_token`) и ставит его в QR.
2. **Ссылка известна до ответа сервера — для чеков без интернета.** Продажа уходит с `Idempotency-Key` (UUID v4, 122 бита случайности). Сервер принимает и такую ссылку: `https://check.nurcrm.kg/c/{idempotency_key}.pdf` → ищет продажу по ключу. Тогда QR можно показать сразу, даже офлайн; пока чек не дошёл до сервера, ссылка отвечает страницей «Чек ещё в пути, обновите через минуту» (HTTP 202), а не 404.
3. **Ответ PDF:** `Content-Type: application/pdf`, `Content-Disposition: attachment; filename="Чек-000123.pdf"` (имя в UTF-8 по RFC 6266), лента 80 мм или A6, кириллица встроенным шрифтом, QR проверки ФД (если ККМ, часть 20), без входа. Камеры iPhone и Android открывают такую ссылку в браузере, и файл сохраняется в «Загрузки».
4. **Защита:** токен — не номер чека (номера подряд перебираются); `public/e-receipt/*` — не больше 30 запросов в минуту с одного IP; срок жизни ссылки — 3 года (срок хранения чеков); отозванный (удалённый) чек — 410.

Приёмка: продажа с телефона → на экране QR → камера другого телефона открывает ссылку → скачивается `Чек-№.pdf` с теми же строками и итогом, что в истории продаж; то же для продажи, проведённой без интернета, после её выгрузки.

## 16. Приёмка (с замерами на тестовом аккаунте, 10 000 товаров)

1. Вход на телефоне до главного экрана — ≤ 1,5 с на 4G (было 3–4 с).
2. Полная загрузка каталога 10 000 товаров — ≤ 5 с. Повторная синхронизация без изменений — один ответ `304` или пустой список, ≤ 200 мс.
3. Две кассы одновременно принимают по 10 шт. одного товара — остаток вырос ровно на 20. Повтор той же приёмки с тем же ключом — не меняет остаток.
4. Продажа: p95 `pos/checkout/` ≤ 400 мс на 100 продажах подряд.
5. Чек без связи с `sold_at` 2 часа назад — в отчёте в своём часе и в своей смене, даже если смена закрылась в 01:00.
6. Повтор `pos/checkout/` с тем же ключом и другим составом → `409 idempotency_conflict`.
7. Ошибки 400/409 содержат `code` из таблицы раздела 4; смена текста `detail` не ломает кассу.
8. «Мои чеки» за смену на телефоне — один запрос, ≤ 200 мс, только чеки этой смены.
9. «Оплата долга» клиента с 10 долгами — один запрос, ≤ 300 мс.
10. `api/health/` отвечает ≤ 50 мс без токена; при остановленной базе — `503` с `"db": "down"`.
11. Список чеков на странице 100 строк — число запросов к базе одинаковое для 10 и 100 строк.
