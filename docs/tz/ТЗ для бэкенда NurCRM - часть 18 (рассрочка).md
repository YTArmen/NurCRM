# ТЗ для бэкенда NurCRM — часть 18: рассрочка

_12.10.2026. Источник — запрос владельца NurMarket: «у нас нет рассрочки, создай дизайн и логику рассрочки оплаты». Макеты экранов — холст «NurMarket — редизайн в стиле Coca», блок «Рассрочка» (доски Р1–Р8)._

## 1. Задача

Покупатель забирает товар сразу, платит первый взнос, остаток — частями по графику. Сейчас есть только «продажа в долг» (один срок, одна сумма). Рассрочка отличается:

- есть **график** — несколько платежей по датам;
- есть **наценка за срок** (может быть 0 %);
- есть **договор** с паспортом клиента;
- просрочка считается **по каждому платежу**, с пеней;
- можно **погасить досрочно** без наценки за оставшиеся месяцы;
- можно **расторгнуть** с возвратом товара.

Рассрочку оформляют касса (Windows, Linux), телефон (Android), веб-касса. Видят и ведут — программа владельца и веб-админка. Клиент видит свой график по ссылке из WhatsApp.

## 2. Настройки компании

Хранить в настройках компании (как остальные `app-settings`), одинаково на всех кассах:

| Поле | Тип | Пример | Смысл |
|---|---|---|---|
| `installments_enabled` | bool | true | функция включена (платная функция `installments` в списке функций) |
| `terms` | массив `{months, markup_percent}` | `[{3,0},{6,6},{9,9},{12,12}]` | доступные сроки и наценка за срок |
| `min_down_payment_percent` | число | 20 | минимальный первый взнос, % от суммы чека |
| `min_check_amount` | деньги | — | кнопка «Рассрочка» видна, если чек не меньше |
| `client_limit` | деньги | — | сколько клиент может быть должен по всем рассрочкам сразу |
| `grace_days` | целое | 3 | льготные дни после даты платежа, без пени |
| `penalty_per_day` | деньги или % | — | пеня за каждый день просрочки после льготных |
| `round_to` | деньги | 10 | платёж округляется вверх до этой суммы |
| `require_passport` | bool | true | без паспорта и фото договор не оформить |
| `block_on_overdue` | bool | true | при просрочке не давать новую рассрочку и долг |
| `reminders` | `{days_before: 3, on_due_day: true, every_overdue_days: 3}` | | напоминания в WhatsApp |

## 3. Модель

```
Installment (договор)
  id, number                 — номер договора (сквозной по компании)
  company_id, branch_id
  client_id                  — обязателен
  sale_id                    — продажа, по которой оформлено (товар списан этой продажей)
  created_by                 — сотрудник
  created_at
  price                      — сумма товаров (цена чека)
  down_payment               — первый взнос
  principal                  — остаток = price − down_payment
  months
  markup_percent             — из настроек на момент оформления (копия, не ссылка)
  markup_amount              — principal × markup_percent / 100
  total_to_pay               — principal + markup_amount
  status                     — draft | active | overdue | paid | paid_early | cancelled
  passport, photo_url        — если require_passport
  closed_at

InstallmentPayment (строка графика)
  id, installment_id, n (1..months)
  due_date
  amount                     — по графику
  paid_amount                — сколько уже внесено в этот платёж
  status                     — pending | partial | paid | overdue
  penalty_accrued            — начисленная пеня по этому платежу
  penalty_paid

InstallmentTransaction (движение денег)
  id, installment_id, created_at, created_by, device (kassa|phone|web|client_qr)
  kind                       — down_payment | payment | early_payoff | penalty | refund
  amount, method             — cash | card | qr | transfer
  shift_id                   — смена кассы, если наличные/карта через кассу
  allocation                 — JSON: [{payment_n, principal_part, penalty_part}]
```

## 4. Расчёт графика (сервер — главный, касса считает так же для показа)

```
principal     = price − down_payment
total_to_pay  = principal × (1 + markup_percent / 100)
base          = ceil(total_to_pay / months / round_to) × round_to
платежи 1..months−1 = base
последний          = total_to_pay − base × (months − 1)
даты: тот же день месяца, что день оформления (31-е → последний день месяца)
```

Пример (числа из макета): цена 50 000, взнос 10 000 (20 %), 6 мес, наценка 6 %.
`principal = 40 000`, `total = 42 400`, `base = ceil(7066,67 / 10) × 10 = 7 070`, пять платежей по 7 070 и последний 7 050. Клиент всего платит 52 400, переплата 2 400.

Проверки при оформлении:
- `down_payment ≥ price × min_down_payment_percent / 100`;
- долг клиента по всем активным рассрочкам + `total_to_pay ≤ client_limit` (если лимит задан);
- у клиента нет просрочки (если `block_on_overdue`);
- есть паспорт и фото (если `require_passport`);
- у сотрудника есть право `installments.create`.

## 5. Платёж — распределение денег

Деньги платежа распределяются по порядку:
1. начисленная и не оплаченная пеня, от самого старого платежа;
2. самый старый неоплаченный платёж графика (`partial` или `pending` / `overdue`);
3. остаток переходит на следующий платёж.

Платёж меньше суммы строки → строка `partial`. Сумма оплаты больше всего долга → лишнее не принимать (вернуть ошибку `overpay` с суммой «к оплате»).

## 6. Просрочка и пеня

Ежедневная задача (cron, 00:10 по времени компании):
- строка `pending/partial` с `due_date + grace_days < сегодня` → `overdue`, договор → `overdue`;
- пеня: `penalty_per_day` за каждый день после льготных, по каждой просроченной строке (`penalty_accrued += …`);
- все строки оплачены → договор `paid` (или `paid_early`, если закрыт досрочно).

## 7. Досрочное погашение

Наценка делится на месяцы поровну: `markup_per_month = markup_amount / months`.
За непрошедшие месяцы (строки с `due_date > сегодня`, по которым ещё не было платежей) наценка не берётся:

```
к оплате = остаток по графику − markup_per_month × непрошедшие_месяцы + неоплаченная пеня
```

Пример: оплачено 2 из 6 (14 140), остаток по графику 28 260, непрошедших 4 месяца → `28 260 − 400 × 4 = 26 660` (+ пеня).

## 8. Расторжение (возврат товара)

- товар возвращается на склад обычным возвратом по `sale_id`;
- сервер показывает: внесено всего, из них наценка и пеня;
- сколько вернуть клиенту — вводит администратор (право `installments.cancel`), операция `refund`;
- договор → `cancelled`, будущие строки удаляются.

## 9. Деньги и отчёты

- Товар списывается со склада продажей при оформлении (как обычная продажа).
- Выручка продажи — полная цена `price`. Наценка — отдельный доход «Наценка рассрочки» (в «Прибыли и деньгах» отдельной строкой).
- В смену кассы попадают только реальные деньги: первый взнос и платежи, своим способом оплаты (`shift_id`).
- Дебиторка «Клиенты должны по рассрочкам» = сумма `total_to_pay − paid` по активным и просроченным договорам.

## 11. Работа без интернета

Касса и телефон без связи:
- **оформить** рассрочку нельзя (нужны проверки лимита и просрочки на сервере) — кнопка показывает «нужна связь»;
- **принять платёж** можно: касса сохраняет транзакцию локально с `client_uuid`, отправляет при связи; сервер распределяет её по правилам раздела 5 на момент получения. Повторная отправка с тем же `client_uuid` не дублирует платёж.

## 12. Напоминания (WhatsApp, тем же механизмом, что напоминания о долге)

- за `days_before` дней до платежа: «Напоминаем: платёж по рассрочке [сумма] до [дата]»;
- в день платежа;
- при просрочке — каждые `every_overdue_days` дней, с суммой пени;
- после каждого платежа — квитанция с остатком и ссылкой на график клиента.

## 13. Что сделает программа после ответа сервера

- кнопка «Рассрочка» в оплате (касса, телефон, веб-касса);
- окно оформления с графиком, договор PDF и печать;
- окно платежа: очередной / за N месяцев / своя сумма / погасить всё;
- раздел «Рассрочки» у владельца и в веб-админке, плитки итогов;
- в карточке клиента — рассрочки и ближайший платёж;
- Нур Советник и Telegram-бот отвечают «кто просрочил рассрочку», «сколько ждём в этом месяце».
