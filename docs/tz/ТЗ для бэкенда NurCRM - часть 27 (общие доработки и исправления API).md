# ТЗ для бэкенда NurCRM — часть 27: общие доработки и исправления API

_12.10.2026. Источник — разбор частей 17–26 и ТЗ для десктопа, телефона на Flutter и веба по просьбе владельца «изучи ТЗ бэкенда и добавь, чего не хватает». Здесь то, что нужно сразу нескольким частям, и известные ошибки сервера из `docs/AI_HANDOFF.md`._

## 1. События в реальном времени (один канал на всё)

Сейчас касса и программа владельца опрашивают сервер. Телефону, вебу и новым функциям нужны мгновенные события.

```
GET  wss://app.nurcrm.kg/ws/events/?token=<JWT>&device_id=…
→ {"type": "...", "id": "...", "branch_id": "...", "at": "...", "data": {...}}
GET  api/main/events/?after=<cursor>&timeout=25     — запасной путь (долгий опрос), тот же формат
```

- **Типы событий:**
  - `payment.intent_changed` (21);
  - `fiscal.registered` и `fiscal.queue_changed` (20);
  - `task.*` (24);
  - `cart_event.suspicious` (24);
  - `esf.incoming` (23);
  - `order.*` (26);
  - `features.changed` и `permissions.changed` (19);
  - `stock.changed` (остаток товара изменился на другой кассе);
  - `catalog.changed`.
- Событие доходит только устройствам компании и филиала, которым оно положено по правам.
- `cursor` позволяет догнать пропущенное после потери связи (хранить события 24 часа).

## 2. Устройства и сессии

Нужно для списка устройств в «Настройках и подписке» (В16), «Отключить устройство», пуш-уведомлений, обмена по сети и веб-кассы.

```
Device — id (uuid с устройства), company_id, branch_id, kind: kassa_windows | kassa_linux | phone_android | phone_ios | web,
         name, app_version, cashbox_id?, last_seen_at, push_token?, revoked_at
POST   api/main/devices/register/     {device_id, kind, name, app_version}   — при входе
GET    api/main/devices/
POST   api/main/devices/{id}/revoke/  — сессии устройства больше не действуют, следующий запрос → 401 device_revoked
```

**Обновление входа.** Нужен `refresh`-токен: `POST api/users/auth/refresh/ {refresh}` → новый `access`. Сейчас касса держит только `access` и при его истечении входит заново. «Выйти на всех устройствах» — `POST api/users/auth/logout-all/`.

## 3. Сотрудники: приглашение и код для кассы

На макетах (В14, О4, К4): «+ Пригласить», «ссылка придёт в WhatsApp», «код для кассы (4 цифры) сотрудник придумает сам».

```
POST api/main/employees/invite/  {phone, name, role, branch_ids}  → ссылка в WhatsApp
POST public/invite/{token}/accept/  {password, kassa_pin}
POST api/main/auth/kassa-pin/  {cashbox_id, employee_id, pin}  → access того сотрудника — быстрая смена кассира на кассе без пароля
```

PIN хранится хэшем. После 5 ошибок — блок на 5 минут и уведомление админу.

## 4. Повторная отправка без дублей — для всех записей

Одно правило вместо разных `client_uuid` в каждой части. Любой `POST`, создающий запись (продажа, платёж, приёмка, событие корзины, задача, бонус, движение остатка), принимает заголовок `Idempotency-Key: <uuid>`. Повтор с тем же ключом в течение 7 дней возвращает **тот же** ответ и ничего не создаёт.

Касса без интернета копит очередь и шлёт её с ключами. Уже существующее поле `client_uuid` считать тем же ключом.

## 5. Продажа одним запросом

Сейчас оплата — три запроса подряд (`start` → `add-item` × N → `checkout`), около 1–2 с. Для скорости, работы без интернета и веб-кассы:

```
POST api/main/pos/sales/checkout-full/
{ shift_id, cashbox_id, client_id?, sold_at?, lines:[{product_id, variant_id?, qty, price, discount?, package_id?}],
  order_discount?, payments:[…], fiscal?: true, loyalty?: {…}, order_id? }
→ продажа с number, fiscal, начисленными бонусами
```

Те же проверки и тот же результат, что у трёх запросов. Старый путь остаётся.

## 6. Резерв товара

Для сборки заказа (26), отложенных чеков и открытых корзин на нескольких кассах:

```
Reservation — product_id, variant_id?, qty, source: order | deferred_cart | cart, source_id, expires_at
```

- **Остаток для продажи** = остаток − резервы. Его отдают каталог, сайт и проверка при `checkout`.
- Резерв корзины живёт 30 минут без действий; резерв заказа — до выдачи или отмены.

## 7. Смена: исправления

| Сейчас | Нужно |
|---|---|
| Внесение уходит как `manual`, и после закрытия баланс меньше на сумму внесений (AI_HANDOFF, открытая задача) | Отдельный вид операции `cash_in`: входит в ожидаемую сумму смены |
| Z-отчёт относит смешанную оплату к безналу | Разбивка `payments[]` (часть 20, раздел 3), в Z-отчёте — по методам |
| Возвраты и внесения в отчёте смены считаются только локально на кассе | В `GET api/construction/shifts/{id}/` — `returns_count`, `returns_sum`, `cash_in`, `cash_out`, `debt_payments`, `by_method` |
| Обмен товара из чека **закрытой** смены завышает `expected_cash` текущей смены на сумму возврата (касса пишет поправку `exchange_cash_fix.json`) | Деньги обмена — в смену, где был обмен, без завышения |
| Обмен с методом `card` сервер отклоняет | Разрешить `card` и `qr` для доплаты и возврата при обмене |

## 8. Каталог: исправления

- после `PATCH` цены или остатка **версия каталога** не меняется — касса пропускает изменения при обычной синхронизации. Нужно: любое изменение товара поднимает `catalog_version` и шлёт событие `catalog.changed`;
- `GET api/main/products/barcode/{code}` не находит штрихкоды вариантов (404) — касса держит свой индекс `variant_barcodes.json`. После части 25 искать и по `ProductVariant.barcode`;
- `GET api/main/products/list/?updated_after=` — подкачка только изменённых (сейчас 10 000 товаров — около минуты, 100 страниц).

## 9. Списки и ограничения

- **Страница после последней** (`pos/sales/?page=3` при 65 чеках) отвечает 500 — нужно 404 или пустой список. Касса сейчас обходит это запросом `count`.
- **429:** добавить заголовок `Retry-After` и задокументировать лимиты (запросов в секунду на токен и на компанию), чтобы касса, телефон и веб не угадывали паузы.
- Во всех списках — `count`, `next` и стабильная сортировка (новые первыми), иначе при подкачке страниц продажи пропускаются или дублируются.

## 10. Отчёты для бота и Сводки

Сейчас отчёты Telegram-бота (`/неделя`, `/топ`, `/abc`) считаются по локальной истории кассы. Нужны серверные:

```
GET api/main/analytics/market/?tab=sales&from=&to=&group=day|week|cashier|branch
GET api/main/analytics/market/?tab=products&from=&to=&top=10&abc=1
```

Плюс сводка «на сегодня» одним запросом для экранов Сводки (В1, ВТ3, Т8):
`GET api/main/dashboard/today/` → выручка, чеки, средний чек, прибыль, по часам, кассиры, способы оплаты, а также плитки новых функций: удаления, платежи без чека, ЭСФ ждут, сертификаты, заказы в сборке, просроченные рассрочки.

## 11. Веб

- CORS для домена веб-админки (`app.nurcrm.kg` или отдельный, например `pos.nurcrm.kg`), только HTTPS;
- веб-касса регистрируется как устройство `web` (раздел 2) и получает `cashbox_id` так же, как касса;
- загрузка файлов (фото товара, фотоотчёт, логотип) — общий `POST api/main/files/` (multipart) → `{id, url}`, ограничения: 10 МБ, jpg, png, webp, pdf.

## 12. Журнал действий

`AuditLog — company_id, employee_id, device_id, action ('price.changed', 'feature.disabled', 'sale.returned', 'shift.closed', 'pin.used'…), object_type, object_id, before, after, at`.

`GET api/main/audit/?employee_id=&action=&from=&to=` — для владельца в вебе. Касса пишет часть действий сейчас в MySQL-аудит; после этой части — на сервер.

## 13. Приёмка

1. Оплата QR на кассе закрывается по событию за ≤ 1 с; при потере связи касса догоняет события по `cursor`.
2. «Отключить устройство» в вебе → телефон получает 401 `device_revoked` и выходит.
3. Сотрудник принимает приглашение и входит на кассе по 4-значному коду.
4. Продажа одним запросом быстрее трёх запросов не менее чем в 2 раза; повтор с тем же `Idempotency-Key` не создаёт вторую продажу.
5. Внесение 5 000 → после закрытия смены баланс совпадает с ящиком.
6. Смена цены в вебе → касса видит её за ≤ 5 с без полной синхронизации.
7. `pos/sales/?page=99` → пустой список, не 500.
