# ТЗ для бэкенда NurCRM — часть 26: заказы с сайта — сборка и выдача

_12.10.2026. Источник — запрос владельца: «собрать заказ с сайта — отрисуй дизайн и функционал после нажатия „Собрать заказ“». Макеты — блок «Заказ с сайта — сборка и выдача» (СЗ1–СЗ5), «Заказы с сайта» (16, В11, Т22, ВТ10, О5)._

## 1. Что есть сейчас

- Заказы витрины: `GET/PATCH api/main/showcase/orders/` (ТЗ часть 3, 6.12). Статусы: `new → accepted → ready → done`, отмена `canceled`.
- Сервер умеет менять **только статус** (`PATCH {status}`). Касса не может:
  - изменить строки заказа (замена, меньше, убрать);
  - записать, кто собирает;
  - выдать код получения;
  - отложить товар под заказ;
  - провести оплату при выдаче как продажу по заказу.

## 2. Статусы и время

```
new        — новый, ждёт ответа
accepted   — принят, «Собираем» (на экране); assembling_by, assembling_started_at
ready      — собран, «Готов к выдаче»; ready_at, pickup_code, bags_count, shelf
done       — выдан; done_at, sale_id
canceled   — отменён; cancel_reason (видит покупатель), canceled_by
```

К заказу добавить журнал `history: [{status, at, by, note}]` — блок «Ход заказа» (СЗ1) и лента в вебе (СЗ4).

## 3. Строки заказа — сборка

```
OrderLine
  id, product_id, variant_id?, name, price, qty_ordered
  qty_picked           — сколько собрано (сканом или «+»)
  status               — todo | picked | partial | missing | replaced | removed
  replaced_by_line_id? — замена: новая строка с другим товаром
  weight_kg?           — весовой товар: фактический вес
```

```
PATCH api/main/showcase/orders/{id}/lines/{line_id}/   {qty_picked}
POST  api/main/showcase/orders/{id}/lines/{line_id}/replace/  {product_id, variant_id?, qty}   → новая строка, старая replaced
POST  api/main/showcase/orders/{id}/lines/{line_id}/remove/   {reason}
POST  api/main/showcase/orders/{id}/scan/  {barcode}  → {line_id, qty_picked} | {error: not_in_order | already_picked}
```

- итог заказа (`total`) пересчитывает сервер после каждой правки;
- скан чужого товара — `not_in_order`, лишнего — `already_picked`;
- штрихкод варианта (часть 25) находит строку с нужным размером.

## 4. Начать сборку

`POST api/main/showcase/orders/{id}/start-assembly/` → `accepted`, `assembling_by` = текущий сотрудник.
- если сборку уже начал другой — ошибка `already_assembling` с именем;
- «Забрать сборку себе» — только админ (`orders.reassign`).

**Резерв:** с этого момента товары заказа зарезервированы (часть 27, раздел 6). Касса не даёт продать последние штуки, отложенные под заказ, а остаток на сайте уменьшается.

## 5. Нет товара

Окно СЗ2. Кандидаты на замену: `GET api/main/showcase/orders/{id}/lines/{line_id}/alternatives/` → товары той же категории или бренда с остатком > 0, ближайшие по цене.

- **«Спросить покупателя»:** `POST …/lines/{line_id}/ask-customer/ {variants:[product_id]}` → сообщение в WhatsApp или Telegram со ссылкой `public/order/{token}/choose/`. Покупатель выбирает заменить или убрать, ответ приходит событием (часть 27, раздел 1).
- **Галочка «Поставить остаток 0 и снять с сайта»** — обычная правка остатка с причиной `not_found_on_shelf` (видна в «Удалено из чека» и ревизии).

## 6. Заказ собран

`POST api/main/showcase/orders/{id}/ready/ {bags_count, shelf, notify: true}`
- не всё собрано → ошибка `incomplete` со списком строк. Повтор с `force: true` — только с подтверждением кассира;
- сервер выдаёт `pickup_code` (4 цифры, уникален среди готовых заказов компании) и `pickup_qr_token`;
- сообщение покупателю: «Заказ [№] готов! К оплате N сом … Код выдачи 4821. Ждём до …»;
- `GET api/main/showcase/orders/{id}/labels.pdf?bags=2` — наклейки на пакеты (58×40, номер, клиент, полка, QR); `…/pick-sheet.pdf` — лист сборки (СЗ3).

## 7. Выдача

1. Поиск: `GET api/main/showcase/orders/?pickup_code=4821` или скан QR наклейки или сообщения (`?pickup_qr=`).
2. Оплата при получении — продажа **по заказу**: `POST api/main/pos/sales/from-order/ {order_id, shift_id, payments[]}` создаёт продажу строками заказа (собранными и заменёнными), с клиентом заказа. Дальше — обычный путь: номер чека, ККМ (часть 20), бонусы (часть 22), списание остатка, снятие резерва.
3. Заказ оплачен онлайн — та же продажа с `payments:[{method: online, reference}]` без денег в кассе.
4. После продажи сервер ставит заказу `done`, `sale_id`.

Доставка: `ready` → `out_for_delivery` (курьер, телефон) → `done` после оплаты курьеру. Курьерскую часть можно сделать вторым этапом.

## 8. Сроки и напоминания

- настройки компании: `assembly_minutes` (20), `pickup_until` (время конца дня) или `pickup_days`;
- не начали собирать за 10 минут → уведомление админу;
- готовый заказ не забрали до `pickup_until` → напоминание покупателю, через N дней — владельцу (на доске 16 уже есть «ждёт выдачи 11 дней»);
- отмена готового заказа снимает резерв и возвращает остаток.

## 9. Права

`orders.assemble` — кассир, кладовщик. `orders.cancel`, `orders.reassign` — админ. Отмена оплаченного заказа — возврат денег тем же способом (часть 21).

## 10. События (часть 27, раздел 1)

`order.new`, `order.assembling`, `order.line_changed`, `order.customer_answered`, `order.ready`, `order.done`, `order.canceled` — касса, телефон и веб видят сборку в реальном времени (СЗ4).

## 11. Приёмка

1. Новый заказ из бота → «Собрать заказ» → `accepted`, сборщик записан, товары в резерве: на кассе последнюю штуку продать нельзя.
2. Скан Кока-Колы два раза → строка 2 из 2; скан чужого товара → `not_in_order`.
3. Сока нет → замена на апельсиновый → итог 520 → 525; «Спросить покупателя» → ответ по ссылке приходит событием.
4. «Заказ собран» → код 4821, наклейки на 2 пакета, сообщение покупателю.
5. Выдача по коду → оплата наличными → продажа строками заказа с номером чека и ФД, остаток списан, резерв снят, заказ `done`.
6. Отмена готового заказа → резерв снят, покупателю ушла причина.
