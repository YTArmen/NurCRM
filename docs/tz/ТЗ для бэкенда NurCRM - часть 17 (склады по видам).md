# ТЗ для бэкенда NurCRM — часть 17: склады по видам товаров

_11.10.2026. Источник — запрос владельца NurMarket: «нужно несколько складов: отдельно склад одежды со своей аналитикой, склад услуг, склад аренды, склад продуктов, склад прокатов»._

## 1. Задача

Один магазин (компания или филиал) продаёт товары разных видов: продукты, одежду и обувь, услуги, вещи в аренду и прокат. Владелец хочет вести их как отдельные склады:

- у каждого склада свой список товаров;
- приёмка, ревизия и списание идут по складу;
- у каждого склада своя аналитика: остаток в деньгах, выручка, прибыль, что заканчивается, что не продаётся.

Склад — это часть магазина, а не отдельный магазин. Продажа идёт через те же кассы и смены, деньги — в ту же кассу компании. Филиалы NurCRM для этого не подходят: филиал — это отдельная точка со своими кассами и продажами.

## 2. Как сделано в программе сейчас (временно, без сервера)

С версии после 1.17.58 в программе владельца (Windows) раздел «Склад» умеет:

- переключаться между складами: «Все склады / Продукты / Одежда и обувь / Услуги / Аренда и прокат / Без склада»;
- держать отдельный склад как группу категорий товаров. Товары-услуги (`kind = service`) попадают в «Услуги» сами;
- считать по выбранному складу плитки итогов (товаров, склад по закупке и продаже, заканчивается, нет в наличии) и вкладку «Обзор» (неликвид, что заказать).

Раскладка хранится в настройках компании, которые уже есть на сервере:

```
GET/PUT api/main/app-settings/nurmarket-owner/   ключ WarehouseZonesJson
```

Значение — JSON-строка:

```json
[
  {"Id": "grocery",  "Name": null, "Categories": ["бакалея", "Напитки", "Сладости"]},
  {"Id": "clothing", "Name": null, "Categories": ["Футболки", "Обувь"]},
  {"Id": "services", "Name": null, "Categories": []},
  {"Id": "rental",   "Name": "Прокат техники", "Categories": ["Аренда оборудование"]}
]
```

`Name = null` — стандартное название на языке интерфейса.

**Чего временное решение не умеет — поэтому нужен сервер:**

1. Склад знают только Windows-программы. Сайт, Android, Telegram-бот и ИИ о складах не знают.
2. Аналитика по складу считается на ПК из каталога. Выручка и прибыль по складу за период недоступны: в продажах нет склада.
3. Нет прав «сотрудник видит только свой склад».
4. Остаток один на товар — разнести один товар по двум складам нельзя.

## 3. Что нужно от сервера

### 3.1. Модель «Склад» (Warehouse)

| Поле | Тип | Описание |
|---|---|---|
| `id` | uuid | |
| `company` | FK | компания |
| `branch` | FK, null | филиал; `null` — основной магазин |
| `name` | string(100) | «Продукты», «Одежда и обувь»… |
| `kind` | enum | `grocery`, `clothing`, `services`, `rental`, `other` — для иконки и поведения (у `services` нет остатка, у `rental` есть сроки возврата) |
| `is_default` | bool | склад по умолчанию: сюда попадают товары без склада. Ровно один на `company + branch` |
| `sort` | int | порядок показа |
| `is_active` | bool | архивный склад не показывается, но история сохраняется |
| `created_at`, `updated_at` | datetime | |

Ограничения:

- имя уникально в пределах `company + branch`;
- удалить склад по умолчанию нельзя — сначала сделать по умолчанию другой.

### 3.2. Привязка товаров к складу

- **Категория → склад:** новое поле `category.warehouse` (FK, null). Это основной способ — так раскладывает владелец.
- **Товар → склад (исключение):** новое поле `product.warehouse` (FK, null), когда у одного товара склад не такой, как у категории.
- **Действующий склад товара** = `product.warehouse` → иначе `category.warehouse` → иначе для `kind = service` склад с `kind = services`, если он есть → иначе склад `is_default`.
- В ответах товаров отдавать готовое поле `warehouse_id` (действующий склад), чтобы кассе не повторять правило.

### 3.3. API складов

```
GET    api/main/warehouses/                    список (?branch=<id|main>, ?include_inactive=true)
POST   api/main/warehouses/                    создать {name, kind, is_default?, sort?}
GET    api/main/warehouses/{id}/
PATCH  api/main/warehouses/{id}/               {name?, kind?, is_default?, sort?, is_active?}
DELETE api/main/warehouses/{id}/?move_to=<id>  товары и категории переходят в move_to;
                                               без move_to, если у склада есть товары, — 409
PUT    api/main/warehouses/{id}/categories/    {"category_ids": [...]} — заменить набор категорий склада.
                                               Категория, бывшая в другом складе, переносится сюда
```

Ответ элемента списка:

```json
{
  "id": "6f1c…",
  "name": "Одежда и обувь",
  "kind": "clothing",
  "branch": null,
  "is_default": false,
  "sort": 2,
  "is_active": true,
  "category_ids": ["a1…", "b2…"],
  "products_count": 148
}
```

### 3.4. Фильтр по складу в существующих запросах

| Запрос | Что добавить |
|---|---|
| `api/main/products/list/`, `api/main/products/` | `?warehouse=<id>` и `?warehouse=none` (без склада); в каждом товаре — `warehouse_id` |
| `api/main/categories/` | в каждой категории — `warehouse_id` |
| `api/main/products/version/` (версия каталога) | менять версию при смене склада у категории или товара — иначе кассы не обновят раскладку |

### 3.5. Документы склада

В приёмку (закупку), ревизию, списание и возврат поставщику добавить `warehouse` (FK, null). Если не передан — склад по умолчанию из действующего склада товаров. В списках документов — фильтр `?warehouse=<id>`.

### 3.6. Продажи — склад в строке чека

В строку продажи (`pos/sales/…`, позиции чека) сохранять `warehouse_id` — действующий склад товара **на момент продажи**. Склад товара могут потом сменить, а выручка прошлых месяцев должна остаться за тем складом, где была. То же для возвратов: склад берётся из строки исходной продажи.

### 3.7. Аналитика по складу

Все отчёты, которые использует программа, принимают `?warehouse=<id>`:

```
api/main/analytics/market/          api/main/analytics/market/summary/
api/main/analytics/pnl/             api/main/analytics/finance/
api/main/analytics/loss-sales/      api/main/analytics/cashflow/
api/main/pos/sales/ (список)        ABC и сезонность (вкладки analytics/market)
```

Новый сводный отчёт для экрана «Склады»:

```
GET api/main/warehouses/summary/?date_from=2026-10-01&date_to=2026-10-11[&branch=…]
```

```json
[
  {
    "warehouse_id": "6f1c…",
    "name": "Одежда и обувь",
    "products": 148,
    "units": 1260,
    "stock_cost": 812400.00,
    "stock_retail": 1310500.00,
    "low_stock": 12,
    "out_of_stock": 5,
    "revenue": 254300.00,
    "cost_of_sales": 151900.00,
    "profit": 102400.00,
    "margin_percent": 40.3,
    "receipts": 187,
    "top_products": [{"id": "…", "name": "…", "qty": 14, "revenue": 18200.00}]
  }
]
```

Строка «без склада» — `warehouse_id: null`.

### 3.8. Права сотрудников

- Новое поле сотрудника `allowed_warehouses` (M2M, пусто — все склады).
- Сотрудник с ограничением видит в каталоге, документах и отчётах только свои склады. Продавать на кассе может всё — касса продаёт весь каталог, если владелец не решит иначе.
- Создавать, менять и удалять склады — только владелец или права «настройки».

### 3.9. Перенос текущей раскладки

При первом запуске новой версии сервера:

- для каждой компании (и филиала) создать склад «Основной» (`is_default = true`, `kind = other`);
- если в `app-settings/nurmarket-owner` есть `WarehouseZonesJson` — создать склады из него (`Id` → `kind` при совпадении с `grocery/clothing/services/rental`, `Name` или стандартное имя → `name`) и проставить `category.warehouse` по названиям категорий (сравнение без учёта регистра и пробелов по краям).

После этого касса перестанет писать `WarehouseZonesJson` и перейдёт на API складов.

## 4. Второй этап (по желанию владельца позже): раздельный остаток

Если одному товару нужно лежать на двух складах одновременно (например, одно платье и в «Одежде», и в «Прокате»):

- таблица остатков `product × warehouse` вместо одного `product.quantity` (общий остаток = сумма);
- перемещение между складами внутри магазина: `POST api/main/warehouse-transfers/` `{from_warehouse, to_warehouse, items: [{product_id, qty}]}` — по образцу `branch-transfers`, со статусами и отменой;
- продажа списывает со склада строки (по правилу из 3.2 или выбранного кассиром).

В первом этапе этого не нужно — достаточно 3.1–3.9.

## 5. Ошибки

| Код | Когда | Текст `detail` (по-русски, касса покажет как есть) |
|---|---|---|
| 400 | пустое имя, неизвестный `kind` | «Укажите название склада» / «Неизвестный вид склада» |
| 403 | нет прав | «Нет прав на настройку складов» |
| 404 | чужой или удалённый склад | «Склад не найден» |
| 409 | удаление склада с товарами без `move_to`; удаление склада по умолчанию; повтор имени | «На складе есть товары — выберите, куда их перенести» / «Сначала сделайте складом по умолчанию другой» / «Склад с таким названием уже есть» |

## 6. Как проверить (приёмка)

1. Создать склады «Продукты», «Одежда и обувь», «Услуги», «Аренда и прокат»; категория «Обувь» → «Одежда и обувь». `products/list/?warehouse=<одежда>` возвращает только товары этой категории, у каждого `warehouse_id`.
2. Товар-услуга без категории попадает в «Услуги»; товар без категории — в склад по умолчанию.
3. Продать товар из «Одежды», затем перенести его категорию в «Продукты». В `warehouses/summary/` за день продажи выручка осталась у «Одежды».
4. `analytics/pnl/?warehouse=<одежда>` = сумма прибыли строк продаж этого склада.
5. Удалить склад с товарами без `move_to` — 409; с `move_to` — товары и категории в новом складе.
6. Сотрудник с `allowed_warehouses = [Продукты]` в `products/list/` видит только продукты.
7. Компания с `WarehouseZonesJson` после обновления сервера получает те же склады и категории.

## 7. Что сделает касса после готовности сервера

- Склад и «⚙ Склады» читают и пишут `api/main/warehouses/…`; раскладка категорий — через `PUT …/categories/`.
- «Обзор» и плитки берут цифры из `warehouses/summary/` (выручка и прибыль за период по складу), а не считают на ПК.
- В Аналитике, Финансах и ABC появится переключатель склада (`?warehouse=`).
- Приёмка, ревизия и списание передают `warehouse`.
- Android-касса и Telegram-бот («выручка по складу одежды») — тем же API.
