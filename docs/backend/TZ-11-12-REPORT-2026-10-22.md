## Решение по 12.2 (двойное уменьшение долга)

`PATCH debts/{id}/` с меньшей суммой раньше делал две вещи: уменьшал `amount` и записывал платёж (остаток = amount - оплаты), поэтому остаток падал дважды.
Выбрано: PATCH вниз по-прежнему считается погашением (платёж + приход в кассу, как требуют существующие тесты `tests_debt_payment_method`), но `amount` возвращается к прежнему значению. Остаток уменьшается один раз, история платежей и кассы сохранена.
Изменение контракта: после такого PATCH в ответе `amount` равен прежней сумме, а погашенное видно в `paid_total`/`balance`. Старый тест `test_debt_v1_patch_cash_increases_shift_drawer` ожидал `amount == 800` (то есть кодировал баг), он обновлён: `amount == 1000`, `balance == 800`.
Если нужен другой вариант (отклонять PATCH вниз с 400), это поменять в `DebtRetrieveUpdateDestroyAPIView.perform_update`.

## Ответы на вопросы

**6. `POST main/pos/sales/{id}/return/`** (`_execute_sale_return` в `apps/main/pos_views.py`):
- `refund_method`: учитывается. `cash` / `original` (по умолчанию) / способ безнала; влияет на то, трогает ли расход ящик смены (`_refund_drawer_effect`), при несовпадении с исходной оплатой создаётся поправка «наличные остались». `offset` (обмен): расход не создаётся, деньги идут в зачёт нового чека. Другие значения не отвергаются.
- `cashbox_id`: учитывается, касса ищется в своей компании; если не найдена или не передана, то касса чека, касса смены, по `cashbox_role`/`branch_id`, затем POS_MAIN. В эту кассу пишется расход `POS_SALE_RETURN`.
- `restock`: пословного поля НЕТ. В `items` разбираются только `sale_item_id` (или `id`) и `quantity`; `restock` в строке молча игнорируется. Возврат товара на остаток определяется одним флагом запроса `is_defect`: `false` (по умолчанию) то товар возвращается на остаток (с учётом упаковки и варианта); `true` то на остаток НЕ возвращается, причина строки = `defect`, для агентских чеков фиксируется брак по партиям. Неизвестные поля не дают 400.
- Для чека в долг возвращаемые деньги = `cash_refund_due` из корректировки долга, остальное гасит долг.

**25.** Да. `POST main/pos/checkout/` принимает `consultant_id`, `consultant_commission_enabled`, `consultant_commission_percent` (`QuickCheckoutSerializer`) и передаёт их в оформление продажи.

**26.** Нет. У `CashShift` нет поля `code`/номера смены (только `id` UUID). У чека есть `doc_number`. Сайт может брать последние цифры id, пока поле не добавят (это миграция в apps/construction).

**27.** Да. `cashier_breakdown[]` содержит `cashier_id` (строка uuid или null), `cashier_display`, `sales_count`, `sales_total`. Фильтр `?cashier=` в `construction/cash/shifts/{id}/sales/` принимается (один id или несколько, фильтр по `Sale.user`, а не по владельцу смены).

**28.** Да. `track_number` есть в `EmployeeCreateSerializer` (`users/employees/create/`) и в `EmployeeUpdateSerializer` (`PATCH users/employees/{id}/`).
